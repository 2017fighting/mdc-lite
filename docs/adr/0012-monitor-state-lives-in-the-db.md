# 0012. 监控是运行时状态，落 DB 不落配置文件；inotify 不实现

- 状态：Accepted
- 日期：2026-10-27
- 来源：wayfinder 票「监控与触发模型」（#10）、「配置文件 schema 与校验」（#8）

## 背景

README 的「设置一个监控」读起来是运行时动作，但配置文件 schema 说「一个配置文件 = 一条完整流水线」、不做层级合并；旧仓把监控目录放在配置文件里。用户环境是 NFS，inotify 在其上本就不工作；README 的轮询防抖写的是「再隔 3s」，而下载中的半个文件进流水线是难以撤销的错。

## 决定

- 监控**落 DB**（`monitors` + `monitor_dirs`，水位线挂在根行），CRUD 走 API/前端；改动**下一 tick 生效**，无需重启。
- 三个触发源（`manual` / `monitor` / `webhook`）**汇入一条接入路径**，只注入 `{roots, exclude}` 覆盖 `scan.with`；`roots` 元素可以是目录或**文件**。
- **范围 = 每根一条持久水位线（ctime）**；**就绪 = 静默窗口**（`(size, mtime)` 稳定 ≥120s）；**提交 = 整组就绪**；存量不刮（走手动扫描）。
- **inotify 不实现**；config 里没有 `mode` 键。
- 校验在创建/更新时（400）：pipeline 存在、`exclude` 是根的真子目录（整棵子树、不认 glob）、跨监控根不重叠；根不要求此刻存在。启动时对存量行再算一遍，悬空 pipeline 引用只停该监控、其余照跑。
- **表形状现在定，迁移随第二批实现落地**（V1 只建 §11 的 7 张 + goose 台账）。

## 替代方案

- 监控写进配置文件：被否 —— 与「一个文件一条流水线」「只重启生效」都冲突。
- inotify（或 inotify + 轮询双模式）：被否 —— NFS 上不工作，留一条只在别处可测的代码路径不划算。
- README 的 3s 防抖：被否 —— 取代为静默窗口（半个文件进流水线代价太高）。

## 后果

- 一处目录只属于一个监控 ⇒ 一个目录只有一条流水线。
- 就绪观测只在内存（丢了只多等一个窗口）。
- 已知边界：组提交后才到的分片会落成第二个同号任务（重复刮削，最终产物仍正确，因为输出是「覆盖但内容相同则跳过」）。
