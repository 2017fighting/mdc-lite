# 0018. 三视图所需的三处端点增量：白名单入口、被过滤清单、按组建任务

- 状态：Accepted（对 ADR-0013「形状现在冻结」与 ADR-0016「端点面完全不变」的显式补充）
- 日期：2026-10-29
- 来源：票 #27（前端三视图与待补号面板）的验收条目；spec #17 §14 与两次修订评论

## 背景

ADR-0013 把 `/api/` 的形状冻结为「改就改一次」，票 #26 按 §14 落了 15 个端点。票 #27 的验收里，有三条**在已冻结的响应里没有数据来源**：

1. **目录工作台的入口与挂载点标签**：`GET /api/fs/dirs?path=` 只回 `{path, dirs}`，既不回 `browse_roots`，也没有 `label`。而验收要求「快捷入口由 `browse_roots` 自身表达：每个根一个可直接进入的条目」「只显示容器内绝对路径 + 挂载点标签」。此外 `path` 必填，前端在拿到第一个根之前**没有任何路径可以问**——鸡生蛋。
2. **扫描页的被过滤清单**：预览只回 `groups[]`，被 `filter` 规则挡掉的文件与规则名完全没进响应，验收要求「被过滤文件折叠在下方并给规则原因」。
3. **按组建任务**：`POST /api/tasks` 只收 `{pipeline, roots[]}`，服务端在 `group` 之后为**每个**组建任务。验收要求「按组勾选」+ 底栏「已选 N 组 / M 文件 · 建任务」——勾选若不改变批次内容，那条底栏就是在骗人。

顺带发现票 #26 的一个投影 bug：`PreviewResult.Matched` 取的是 `FilterSummary.Out`，而 `filter` 步骤把 **`In` 记为收录、`Out` 记为排除**（`filter.go`），于是「进候选数」显示成了「被排除数」。

## 决定

四处都是**增量**，不新增端点、不新增错误码、不改变已有字段：

- `GET /api/fs/dirs` 响应增加 `roots:[{path,label}]`（= 完整 `browse_roots`，`label` 空时回落为 `path`）与 `label`（当前路径所属**最内层**根、即前端 `mountLabel` 的同一条规则；嵌套根时两处一致）。
- `GET /api/fs/dirs` **`path` 缺省**改为引导响应 `200 {path:"", label:"", roots:[...], dirs:[]}`：只回白名单，**不列任何目录**。原来的 `400 bad_request` 由这一条取代——它不是「列全部」，因为白名单本来就在每个成功响应里。
- `GET /api/scan/previews/{id}` 响应增加 `filtered:[{path, rule}]` 与 `filtered_total`；列表上限 `PreviewFilteredLimit = 200`，`filtered_total` 是真实总数（与 `dirs` 上限同一个理由：一次响应不该随目录规模无限长大）。
- `POST /api/tasks` 增加可选 `groups[]`（被勾选组的主片路径）。缺省 = 走到的每个组（CLI 与 curl 的既有调用不受影响）。过滤发生在**同一次前缀之后**，所以「预览里看到的分组」就是「这里能选的组」；选中的主片一个都不在 walk 里时回 `400 empty_selection`（树变了，不该静默建空批次）。被漏选的组不进 `skipped[]`：它不是被过滤、也没被占用，只是没被选中。
- `PreviewResult.Matched` 改为 `FilterRun.In`（收录数），并补契约测试钉住「5 走过 / 4 进候选 / 1 被过滤」。

## 不变量（未改）

- 端点数量仍是 15；写操作仍是 POST + JSON；错误码集合不变。
- 可浏览范围仍只由 `browse_roots` 白名单决定；路径只显示容器内绝对路径，不做宿主映射与拖放。
- `groups[]` 不绕过 `filter`、不绕过 `path_occupied` 去重闸、不改 `group` 的分组判据。
- `filtered` 只回 `filter` 判掉的文件；`scan` 自己的跳过（hidden / excluded / partial）仍是 `scan` 摘要的事，不进这张表。

## 替代方案

- **(a) 前端硬编码 `/media` 作入口、再凭报错猜白名单**：被否 —— 默认配置是 `/media`，但配置可改；猜错误消息是在拿文案当协议。
- **(b) 让 `POST /api/tasks` 的 `roots` 承载勾选（把每个选中组的主片当根）**：被否 —— 与 §13「用选中路径覆盖 roots 建批次」的语义（`roots` 是目录、走整棵树）冲突，也会让 `trigger_ref` 指的路径不再是用户选的目录。
- **(c) 为一个前端页面新开 `/api/fs/roots` 与 `/api/tasks/preview-selection`**：被否 —— 端点面翻倍只为省两个字段。
- **(d) 前端不显示被过滤清单 / 勾选只做确认不做过滤**：被否 —— 前者缺一条验收，后者让底栏的计数成为假信息。

## 后果

- 三个响应字段与一个请求字段进了契约；再有改动应优先复用（例如监控目录的 CRUD 也用同一个 `roots` 列表）。
- `filtered` 的上限意味着「前 200 条 + 总数」，UI 必须显示这条说明。
- 票 #26 的契约测试里「`path` 缺失 → 400」被「引导响应」取代，测试同批更新；`Matched` 的期望值从「非零」收紧为精确值。
