> 整体采用pipeline设计，可以自由组合，增删步骤

## 跑起来

```
make build          # CGO_ENABLED=0 静态单二进制（前端产物内嵌）
make check          # PR 门禁：vet + test + lint + 前端 typecheck
make config-check   # 打印 examples/ 的流水线与生效键及其来源

bin/mdc config check --config /config/config.yaml
bin/mdc serve        --config /config/config.yaml
bin/mdc run          --pipeline main --roots /media/in --until group --dry-run
```

`mdc run` 跑一条流水线并打印一次扫描的摘要（walk 了多少、进了多少候选、滤掉多少及原因、
分了哪些组），不写盘不落库；`--until` 决定停在哪一步。

配置是两份、互不合并：`/config/config.yaml`（进程级，可选、全键有默认）与
`/config/pipelines/*.yaml`（一条流水线一份，`id` = 文件名字干）。写错一个键名就拒绝启动，
报错形如 `config/pipelines/main.yaml:14:5: step 3 (scrape): unknown field "plot_prioirty"`。
示例配置在 `examples/`，首次启动不会生成任何文件。

## 整体流程

0. 设置一个监控：轮询模式，监控目录[/mnt/path/a, /mnt/path/b]，排除目录[/mnt/path/a/ignore]，使用配置文件1
1. 监控扫描/手动扫描 得到一个文件列表
2. 根据配置文件，计算哪些文件可以进入候选处理列表
3. 对候选处理列表进行分组，每个分组都对应一个任务(同一个分组的多个视频，按照字母顺序进行排序，排序第一的作为primary，后面处理全都按照这个primary来算)
4. 解析文件名
5. 根据番号进行并发爬取
6. 下载图片，处理图片
7. 翻译标题、简介
8. 名称归一化（标签、演员姓名）
9. 生成nfo

## 监控模式

> 可以配置多个监控，多个监控的监控目录不能重叠，可以指定这个监控扫描到的新文件用哪个配置文件进行处理

监控模式：只支持轮询（NFS 上 inotify 本就不工作，轮询是唯一可靠路径）
监控目录: 支持同时监控多个目录
排除目录：在监控目录里不想监控某些目录（整棵子树，不认 glob）
使用的配置文件：引用一条 pipeline 的 id；监控是运行时状态，在界面/API 里增删改（存 DB，不落 config.yaml）

### 轮询

> 明确提醒用户，不要将下载器的下载中目录加入监控目录

1. 每根一条持久水位线：文件的 ctime 晚于水位线才进视野（存量不刮，要刮存量走手动扫描）
2. 每隔30s（可配），扫描监控目录（跳过排除目录），取水位线之后的新文件
3. 就绪判定：同一个 size/mtime 至少稳定 quiet_window（默认120s）才算写完；没静下来的文件本轮跳过，只记日志
4. 按组提交：整组（分片算一组）都就绪才交给流水线；未就绪的组只记日志、不建批次
5. 水位线推进：本轮新文件全部交出去、且扫描无错时，推进到本轮扫描开始时刻 − quiet_window

### inotify（不做）

NFS 上 inotify 本就不工作，轮询是唯一可靠路径；留一条只在别处可测、线上不走的代码路径不划算。将来真要在本地盘上用再加。

## 配置文件

> 可以创建多个配置文件，用来编排不同的处理流程

### 哪些文件能进入候选处理列表

一个规则列表：满足某些条件->执行某个动作
例如:

1. 文件后缀 in [.srt, .ass] => 加入
2. 文件大小 < 100 MiB => 排除
3. (无条件,永远true) => 加入

### 对候选处理列表进行分组

VR视频大多都是分成多个cd的，比如[SSVR-122-cd1.mp4 SSVR-123-cd2.mp4] [ABC-123-A.mp4 ABC-123-B.mp4] [ABC-123-1.mp4 ABC-123-2.mp4] [9ofje121A.mkv 9ofje121B.mkv]，这种要当成同一个进行统一处理

由于后面还需要根据正则来匹配番号，如果不分组的话，很难写一个比较好的正则来同时匹配番号和cd part(很容易分不清这两部分)

这里只提出一种解决方案：
前提:

1. 只有同目录下的才可能被分到同组
2. 不同分片视频的文件名Levenshtein 距离<=2

由于Levenshtein 距离的计算比较慢，所以只对同目录下的视频进行计算，如果某个目录下的视频文件数量太多，则转而使用B-K Tree，至此，我的解决方案如下：

1. 遍历候选处理列表中的视频文件
2. 按照父目录进行分组
3. 某个分组中有多个视频，如果视频数量少于n，则按照有界 Levenshtein 距离进行分组，否则构建B-K Tree进行分组

### 解析文件名

主要还是解析番号，(是否破解-U，是否中文字幕-C 之类的我不需要，可以先不实现)

可以配置一系列正则，从上往下依次匹配，直到第一个匹配上为止(所以需要越具体的越要放到上面)

- [ ] 是否存在某个刮削器，需要自定义番号解析规则

### 刮削器

输入：番号
过程：根据番号搜索到详情链接，爬取详情内容，下载图片
输出：各个字段 图片二进制(注意有些网站的图片是加密的，想获得图片内容，必须要调用对应刮削器的解密逻辑)(网页上展示原始链接以及图片内容)

### 字段

#### 必选的(必须配置刮削器)

- title: 标题(可能是中文、英文、日文)
- plot: 简介(可能是中文、英文、日文)
- fanart: 横版背景图 16:9
- extrafanarts: 剧照列表
- tags：标签，类型是一个数组
- releasedate: 发布日期，类型是date
- actors: 演员 列表

#### 可选的(可以不配置任何刮削器)

- poster: 海报，竖版封面，通常为1000x1500
- director: 导演
- runtime: 影片时长，单位分钟
- rating：评分，满分10分
- :系列
- 发行商
- ...

#### 处理后的

- poster.crop: 根据fanart右侧裁剪得来
- title.cn: 中文标题(经过翻译器翻译来的，或者刮削器可以直接抓到的)
- plot.cn: 中文简介(经过翻译器翻译来的，或者刮削器可以直接抓到的)
- tags.cn: 归一化后的标签 日文转中文 繁体转简体
- actors.cn: 归一化后的演员列表

#### 内置的

- number: 前面提取的番号

### 调度器

假设现在有A、B、C三个刮削器，按如下配置了字段刮削优先级
title: A,B,C
plot: B,A
tags: B,C

fallback策略

1. 第一次只会将A和B加入队列（因为title第一个是A，plot和tags的第一个是B)
2. 如果A和B都正常爬取到了，就结束了，不会爬C
